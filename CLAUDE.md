# Академія чарівних світів — правила проекта

Браузерная 3D-игра для ребёнка 6–7 лет (Three.js + TypeScript + Vite, PWA). Обзор и команды — в `README.md`.
Требования, этапы и открытые решения — в `docs/` (начинать с `docs/README.md`).

## Приватность — репозиторий публичный

- **Имя ребёнка никогда не попадает в репозиторий**: ни в код, ни в тексты реплик, ни в документы,
  ни в сообщения коммитов, ни в звуковые файлы. Имя — переменная, которая живёт только в сохранении
  на устройстве.
- Коммиты — только с адресом `noreply` GitHub; он настроен в локальном конфиге репозитория, не менять.
- Защита стоит в хуках `tools/hooks/` (проверяют добавленные строки, имена файлов, сообщение коммита
  и адрес автора). Включить один раз в каждой копии репозитория: `git config core.hooksPath tools/hooks`.
- Список запретных слов лежит вне репозитория: `~/.config/academy/private-words.txt`, по слову или основе
  слова в строке. Без списка хук предупреждает и пропускает. `--no-verify` не использовать.

## Ветки и публикация

- **Вся работа идёт в ветке `dev`.** Отправка `dev` в `origin` ничего не публикует. В `dev` вливает, отправляет
  и публикует только ведущая сессия («Параллельная работа»); остальные приносят ей ветки `run/<имя>`.
- **`main` — опубликованная игра** (`https://svv2602.github.io/academy/`). Каждая отправка в `main` пересобирает
  и обновляет её (`.github/workflows/pages.yml`). Ребёнку игра **пока не отдана**: отдадут, когда будут готовы все миры
  (решение заказчика 2026-11-15). До тех пор на опубликованной версии играет только заказчик (проверки на S22) — его
  тестовый прогресс беречь, но без перестраховки «телефона ребёнка»; механизмы, защищающие прогресс (перенос формата
  сохранения, резервная копия), всё равно делать и проверять тестами — они понадобятся, когда игру отдадут.
- В `main` попадает только проверенное состояние `dev`, перемоткой (`git merge --ff-only dev`),
  и **только по прямой команде пользователя в текущей сессии**. Разрешение из прошлой сессии не действует.
- «Проверенное» значит: на этом самом коммите прошли `npm test` и `npm run e2e`. Автоматически это делают
  два workflow: `.github/workflows/ci.yml` — на каждую отправку в любую ветку, кроме `main` (в том числе
  в `dev`), и на pull request; `.github/workflows/pages.yml` — на отправку в `main`: тесты, сборка
  и автопрохождение собранной игры идут до публикации, при падении игра на телефоне не обновляется.
  В обоих workflow (ARCH-15) тесты и сборка идут один раз, четыре размера экрана играются параллельными заданиями
  `walkthrough <размер>` на этой сборке, а итоговое задание `check` падает, если упало что угодно из них, и проверяет
  над их результатами то, что требует всех размеров сразу (`npm run e2e -- --combine <папка>`). Имя `check` требует
  защита `main` — задание не переименовывать. Весь запуск — около 10 минут.
- Перед отправкой в `main` убедиться, что публикуемый коммит зелёный:
  `gh run list --workflow ci.yml --branch dev --limit 1 --json headSha,conclusion` — `headSha` равен
  `git rev-parse dev`, `conclusion` равен `success`. Если такого запуска нет, он не завершён или раннер
  не смог выполнить автопрохождение — обязательно локально на этом коммите: `npm test && npm run e2e`.
- Ветка `main` на GitHub защищена (с 2026-11-13): отправка принимается только для коммита, у которого есть
  зелёная проверка `check` из `ci.yml`; правило действует и для владельца, принудительная перезапись и удаление
  ветки запрещены. Отклонённая отправка в `main` значит, что этот коммит не проверен: дождаться `ci.yml` на `dev`,
  а не обходить защиту.
- Прямых коммитов в `main` нет.
- **Сохранение четвёртой версии** (ARCH-07, LEARN-03, LEARN-15, `src/core/save.ts`): общая часть (облик, звёзды, навыки, закрепление уровней, время игры, покупки,
  достижения, настройки, качество) лежит плоско наверху; прогресс мира — `save.worlds[<id мира>]` (`quests`, `final`, `starsTaken`, `flags`, `pos`; сундук первого мира —
  `flags.chest`). Игра трогает его только через `g.ws`, сценарий читает `__game.save.worlds.fairy`. Навыки — девять по лестнице (`src/game/skills.ts`: `count`, `add`, `sub`,
  `compare`, `series`, `pattern`, `memory`, `classify`, `compose`; у `compose` уровни 3–5, у остальных 1–5); `fixed[<навык>]` — уровень, закреплённый родителем (0 — адаптивно);
  `playMinutes['YYYY-MM-DD']` — минуты игры по дням, последние 7. Перенос цепочкой: v1 — всё, кроме этапа старого среза (звёзды, облик, крылья наверх; собранные звёзды,
  место и сундук — в `worlds.fairy`), v2 — поля мира в `worlds.fairy`, v3 — счётчики `logic` копируются в `series`, `pattern`, `memory`, `classify` (сам `logic` не хранится),
  общая `difficulty` становится `fixed` каждого навыка в его пределах, `compose` начинает с уровня 3; v4 и новее — как есть (неизвестные поля, навыки и чужие миры
  сохраняются, версия не понижается). Новая версия формата — только с переносом и тестом «прочитать — записать» с неизвестным полем.
- **Резервные записи сохранения** (TECH-11): `amw-save-v<N>` — текст старой версии перед переносом (пишется один раз, не
  перезаписывается), `amw-save-prev` — сохранение, прочитанное при прошлом запуске, `amw-save-damaged` — нечитаемая запись;
  при ошибке чтения (в том числе неизвестная версия) игра берёт `prev`, затем `v3`, `v2`, `v1`. Нет основной записи — новый игрок; `clearSave` удаляет все `amw-save*`.
- **После публикации сохранения v4 нельзя откатывать `main` на коммит до него**: старый `loadSave` прочитает `v: 4` как «более позднюю версию», но не найдёт
  в ней `logic` и `difficulty` — навыки логики начнутся с первого уровня, закрепление сбросится. Только исправление вперёд (то же для v3 — его `loadSave` до v3 не читал).

## Проверка перед коммитом

    npm test                                         # юнит-тесты (Vitest, src/**/*.test.ts и tools/**/*.test.mjs), около 15 секунд
    npm run build                                    # проверка типов и сборка
    npm run e2e                                      # сборка, автопрохождение мира в размерах телефона и компьютера
                                                     # (компьютер — без сети), проверка вёрстки каждого экрана, запросов,
                                                     # списка моделей и ссылок; около 10 минут с видеокартой
    npm run e2e -- --all-sizes                       # то же в четырёх размерах экрана, один за другим; около 20 минут
                                                     # (CI играет каждый размер четырьмя кусками мира параллельно — 16 заданий
                                                     # --mode <размер> --only <кусок>, затем --combine <папка> --only world1,world2,finale,shop)
    npm run e2e -- --skip-build --mode mobile        # быстрый вариант: уже собранный dist/, только телефон; около 5 минут
    npm run e2e -- --mode mobile --only shop         # один кусок мира с готовым сохранением (tools/e2e-saves.mjs), 1-3 минуты:
                                                     # world1 (единорог, лиса, вступление, кот), world2 (грибной король, королева,
                                                     # сортировка, настройка, столкновения), finale (олень с поиском, финал, книга,
                                                     # родители, «начать заново»), shop (героиня, вещи, лавка, вывеска; с mobile —
                                                     # экраны сбоев и обновление); tasks — все друзья подряд. Для волн и мутаций;
                                                     # перед публикацией — полный npm run e2e
    npm run voice:sync -- --check                    # список реплик для записи совпадает с текстами игры (после правки строк —
                                                     # npm run voice:sync и закоммитить voice/phrases.json)
    npm run e2e -- --update-models                   # после добавления или удаления модели: переписать tools/models-used.json
    npm run assets                                   # после правки models-src/: пересобрать public/models (сжатие моделей и текстур)

Автопрохождение обязательно после любого изменения игрового кода. `npm run e2e` завершается с ненулевым кодом,
если в консоли есть ошибка или предупреждение, задание зависло, запрос не удался или ушёл на чужой адрес,
нарушена вёрстка экрана (строка `layout: …`), в сборке есть внешняя ссылка, либо сборка без голоса больше 12 МБ, голос (`dist/voice/`) больше 4 МБ или в ней есть файл больше
1 МБ (шаг `dist size`, `tools/dist-size.mjs`); успех — строка `[e2e] PASSED` и код 0. Сервер разработки команде не нужен:
она сама собирает игру и поднимает её на свободном порту начиная с 4183 (`E2E_PORT` задаёт первый порт).
Скриншоты — в `shots-e2e/`. На машине без видеокарты: `E2E_GL=swiftshader Q=0 npm run e2e` — около 10 минут
(с `--all-sizes` — примерно вдвое дольше, не замерено).
Все флаги и переменные окружения: `npm run e2e -- --help`.
Зерно (ARCH-08): `E2E_SEED=<текст>` добавляет к адресу `&seed=<текст>` — игра берёт задания из этого зерна; каждый проход
печатает `task sequence (seed …): N tasks, <отпечаток>` и пишет список в `shots-e2e/<размер>-tasks.txt`. Два прохода одного
размера с одним зерном дают один отпечаток (проверено 2026-11-15: 27 заданий, `mobile`).
Медленная машина (раннер CI с программной отрисовкой): кадр игры считается не длиннее 0,05 с, поэтому игровое время там идёт
в разы медленнее настоящего, а анимации CSS растягиваются на секунды. Сценарий поэтому меряет движение и плавные величины
(шаг героини, расстояние и наклон камеры) в игровом времени (`__game.time`, только с `?debug`), касается кнопки только после
того, как она и её панель перестали въезжать, и снимает кадр с проверкой вёрстки только после анимаций появления
(`rise`, `pop`, `pop2`, `fade`). Новую проверку с ожиданием писать так же: по игровому времени или по событию, не по часам.

Вёрстка: в каждой точке, где прохождение делает скриншот (старт, игра, каждое задание и подсказка, карточки, книга,
родительский раздел), экран измеряется: документ и панели не прокручиваются, каждая панель, кнопка и поле ввода целиком
в окне, кнопки не перекрывают друг друга, облачко реплики не закрывает кнопку, каждая кнопка не меньше 44×44 пикселей.
Нарушение — строка `layout: <размер> <экран>: <элемент> …` и ненулевой код; исключений из правила 44 пикселей в проверке нет.
В каждом виде задания с подсказкой сценарий делает **три** намеренные ошибки (подсказка в три ступени, LEARN-10) и после каждой ждёт,
пока отзвучат «попробуй ещё» и реплика ступени и отработает её показ (метка `#taskStage[data-shown=N]`, у бабочек `__game.bf.shown`), затем
проверяет экран: ступень 1 — ничего не выдаёт ответ (нет цифр над предметами и чисел над группами, точек, `grow`/`shrink`, `alike`, `units`,
`pulse`, `watch`, дорожки, примерки корзин, `hit`; иначе `hint step 1: …`), кадр `hint1-<вид>`; ступень 2 — показ решения на экране и ещё
ничего не пульсирует (`hint: …`), кадр `hint-<вид>`; ступень 3 — пульсирует ровно верный ответ (`hint step 3: …`), кадр `hint3-<вид>`.
Вид, где сделаны не все три ошибки, — `no deliberate mistake was made in: …`. Поэтому адаптивная сложность в сценарии не растёт; чтобы пройти и измерить задания старших уровней,
размерам задан уровень: `mobile` и `mobile-portrait` — третий, `desktop-tall` — второй, `desktop` — адаптивный
(`E2E_LEVEL=<1..5>` закрепляет один уровень всем навыкам во всех размерах, каждому в его пределах: у состава числа 1–2 становятся 3).
Сценарий также дважды закрывает задание с бабочками его кнопкой и возвращается к нему, сверяет навыки до и после
поиска звёзд и по одному разу намеренно ломает разговор и финал (`__game.failNext()`), проверяя, что героиня снова
ходит. Ошибка `scene "…" failed: Error: broken on purpose by __game.failNext()` в консоли в этот момент — ожидаемая;
любая другая ошибка и та же ошибка в другой момент — падение.
Голос в сценарии: после вступления касание кота повторяет его реплику, героиня при этом стоит; после первого осколка
(кнопка карточки нажата, пока персонаж ещё говорит), после второго (нажата, когда он договорил) и после финала реплика
кота ждётся вместе с субтитром — после конца сцены, иначе конец сцены стёр бы её облачко;
пятая звезда у оленя — и в том же кадре разговор с персонажем, чья цепочка закончена:
приветствие и вопрос задания должны доиграть до конца, облачко не показывает непроизнесённых реплик, касание облачка
перезапускает клип вопроса только после его конца, задание закрывается кнопкой без записи.
Поиск звёзд проходится дважды: после первого (с разговором в кадре пятой звезды) сценарий возвращает в памяти цепочку
оленя к началу и ищет звёзды ещё раз; пятая звезда второго поиска — в тишине: клип `tap_5` («п'ять») обязан доиграть
до конца, и только потом стартует похвала `praise_*` (иначе строка `fifth star: …`). Во время первого поиска, после
первой звезды, сценарий говорит с персонажем, чья цепочка закончена, и закрывает его задание крестиком: облачко снова
показывает поиск — ключ `t_stars`, счётчик `⭐ n / 5`, без голоса и его вопрос (иначе `star search after a closed task: …`).
Там же сценарий говорит с оленем: пока звучит его вопрос и после конца сцены облачко — поиска (ключ `t_stars`, счётчик
`⭐ n / 5`, без голоса и вопрос; иначе `talk to the deer during the search: …`). Затем одну законченную цепочку возвращает
в памяти на последний шаг и решает её задание: после осколка «иди дальше» (`go_next`) не звучит и не отбрасывается
планировщиком, облачко остаётся у поиска (иначе `a shard during the search: …`). Задание во время поиска решается при
`search.active = false` на один вызов `__game.cheat()` — иначе тот ставит героиню на звезду.
В конце прохода строка
`lines turned away by the planner: …` перечисляет реплики, отброшенные планировщиком (`src/core/voice.ts`; `audio.ts` ре-экспортирует): допустимы
только `go_next` и `t_stars_back`, любая другая — падение, как и открытое задание, о котором планировщик не знает.
Без голоса: проход `desktop-tall` (шаг `walkthrough desktop-tall (no voice)`) играется с громкостью голоса 0 — она
записана в сохранение до загрузки игры, как это делает ползунок родительского раздела. Каждый клип обязан стартовать
с нулевой громкостью, а на каждом кадре задания и подсказки облачко обязано показывать вопрос этого задания (строка
`question: …`); в поиске звёзд вопрос остаётся и после шести секунд, и рядом со счётчиком найденных. В остальных
проходах голос включён, и на кадре подсказки в облачке подсказка. `E2E_MUTE=<0|1>` задаёт одно всем размерам;
с `--all-sizes` шаг `silent walkthrough` падает, если ни один проход не прошёл без голоса.
Кадр второй ступени (`hint-<вид>`) в любом проходе снимается, когда показ решения уже на экране: цифры на предметах, числа
над группами и растущая или сжимающаяся верная группа («больше / меньше»), общая рамка похожих картинок («что лишнее»),
подсвеченные звенья ряда, пульсирующая кнопка или корзина, повтор показа, счёт кота у бабочек. Показа нет — строка
`hint: …` и ненулевой код. У парных карточек подсказки нет: они открываются показом всех картинок.
Отладка (ARCH-11): `window.__game`, счётчик кадров и панель подбора управления (кнопка ⚙) есть только с `?debug` в адресе
или на сервере разработки; инструменты в `tools/` добавляют параметр сами. Сценарий один раз открывает собранную игру
без `?debug` и проверяет, что их нет, и проверяет ползунки панели (`32-tuning`).
Ещё сценарий: скрывает страницу во время вступления (реплика встаёт на паузу и потом звучит дальше), после самоснижения
качества перезагружает игру и ждёт пониженного уровня, перебирает кнопку качества родительского раздела, закрывает крестиком
каждый вид панельного задания при первой встрече (сохранение не меняется, героиня ходит, потом задание решается) и следит,
чтобы число звёзд ни разу не уменьшилось, а выигранные звёзды в том же кадре были уже записаны в сохранение; между сценами счётчик кристаллов равен числу законченных квестов (иначе `crystals: …`). Шаг `failure screens` (`tools/failures.mjs`, один раз за прогон — с размером
`mobile`): Chrome без WebGL видит сообщение без ошибок в консоли; с заблокированной моделью игра повторяет загрузку, показывает
сообщение и кнопку «Спробувати ще раз», после снятия блокировки и нажатия появляется «Грати». В CI задание `check` требует,
чтобы задание телефона этот шаг прошло.
Шаг `update` (`tools/update.mjs`, один раз за прогон — с размером `mobile`, TECH-13): свой сервер отдаёт сборку, потом её копию
с меткой («новая версия»); во время игры новый сервис-воркер устанавливается и ждёт (`reg.waiting`), страница не меняет воркер
(`controllerchange` нет), не перезагружается, задание решается; после закрытия всех страниц игры новая страница — новая версия
с теми же звёздами. В `vite.config.ts`: `registerType: 'prompt'`, `clientsClaim: true` (без него офлайн-проход ждёт `controller`),
`skipWaiting: false`; сообщение `SKIP_WAITING` игра не шлёт. Новая версия на телефоне — только после закрытия всех окон игры
(свернуть мало).
Родительский раздел в сценарии: пример замка читается с экрана; первая цифра ответа и неверное число раздел
не открывают, верный ответ открывает, второе открытие задаёт другой пример. Номер коммита в строке версии сверяется
с `git rev-parse --short HEAD` исходников (строка `version: …`): после нового коммита `--skip-build` со старым `dist/`
падает — нужно пересобрать.
Перед последней перезагрузкой сценарий переносит героиню в точку 2,5 / 12,5 и проверяет, что уход со страницы сохранил
именно её (иначе строка `leaving the page: …`).
После каждого законченного друга: «все осколки собраны» (`all_shards`) звучит только после последнего (иначе `all shards: …`).
Книга: после её кадра сценарий сверяет осколки (по одному на друга, горят у законченных), звёзды и сундук с сохранением
(иначе `book: …`); порядок друзей первого мира — единорог, лиса, грибной король, олень, королева (иначе `friends: …`).
Столкновения: героиня ставится в 2,5 м перед первым персонажем и полторы секунды игрового времени идёт на него — ближе 1,1 м
к его центру подойти не должна (иначе `collisions: …`).
В самом конце сценарий нажимает «Почати спочатку» на стартовом экране и проверяет, что после перезагрузки сохранение — как у
нового игрока: ни звёзд, ни квестов, ни кристалла, кнопки «начать сначала» нет (иначе строка `start again: …`). Игра
сохраняется при уходе со страницы, поэтому после `clearSave` запись выключена до следующей загрузки (`src/core/save.ts`).
Другой мир реестра (ARCH-06): `E2E_WORLD=<id> npm run e2e -- --mode mobile` играет мир `<id>` вместо первого (`?debug&world=<id>`).
Сохранение v3 заранее содержит прогресс первого мира в `worlds.fairy`; сценарий проходит цепочку каждого персонажа из `__game.npcs`
(телепорт, кнопка действия, `__game.cheat()`), снимает кадры с проверкой вёрстки, сверяет счётчик `<готово>/<персонажей>` и звёзды;
после перезагрузки прогресс лежит в `worlds.<id>`, а `worlds.fairy` не изменился; дальше общие проверки (книга, голос, планировщик,
«Почати спочатку»). Сценарии первого мира в этом режиме не играются; `E2E_WORLD=fairy` — ошибка.
Новый мир — папка `src/worlds/<id>/` (`index.ts` и `strings.ts`, в `strings.ts` только `import type`/`declare module`) и одна запись
в `WORLDS` в `src/worlds/index.ts`; опубликованная игра играет мир `DEFAULT_WORLD` (там же, явный id `'fairy'`), порядок списка
не важен. Каждый мир задаёт свой `subtitle` (подзаголовок стартового экрана, ключ `WORLD_OWN` в `src/ui/strings.ts`, не произносится). Проверка — `npm test`, `npm run build`, `E2E_WORLD=<id> npm run e2e -- --mode mobile` (проверено 2026-11-15
пробным миром с одним персонажем: только новые файлы и строка реестра; после проверки удалён).
Мир кладёт свои отладочные объекты в `debug.more` — они попадают в `__game` как есть (у первого мира `search`, `bf`, `sorting`,
`worldSort`). `__game.worldSort()` — отладочный показ «сортировки» в мире (`src/game/worldtasks/sort.ts`, то же описание, что
у панели); ничего не записывает; сценарий один раз закрывает его крестиком и один раз решает.
Размеры: `mobile` 844×390 и `desktop` 1280×720 играются всегда; `--all-sizes` добавляет `desktop-tall` 1280×800
и `mobile-portrait` 390×844 — оба workflow запускают именно так. После правки `src/style.css` или разметки — `--all-sizes`.

Проход в размере компьютера идёт без сети (шаг `walkthrough desktop (offline)`; `--mode desktop` — тоже): после первой
загрузки скрипт ждёт, пока сервис-воркер положит в кэш весь свой список, отключает сеть, перезагружает страницу
и проходит весь мир; запрос, который не удался без сети, — ошибка. Остальные проходы идут с сетью.
Новый тип файлов, который запрашивает игра, нужно добавить в `globPatterns` в `vite.config.ts`, иначе этот шаг упадёт.

Модели: `tools/models-used.json` — список файлов из `public/models`, которые страница запросила за оба прохода.
Шаг `models used` в `npm run e2e` падает, если запросы разошлись со списком; `npm test` падает, если в `public/models`
есть файл не из списка или наоборот. После добавления или удаления модели: `npm run e2e -- --update-models`
и закоммитить список. Модель, которую игра не загружает, лежит в `models-unused/` (в сборку не входит).

Сжатие моделей: исходники (`.glb` и текстуры) лежат в `models-src/` и в сборку не входят; `public/models/` целиком пишет
`npm run assets` (`tools/assets.mjs`) и руками не правится. Геометрия и анимации сжаты без потерь (`EXT_meshopt_compression`,
без квантования: `src/core/assets.ts` читает те же `Float32`-массивы, декодер встроен в сборку), текстуры — WebP не больше
1024 по большей стороне (цветовые — с качеством 90, карты нормалей — без потерь), отдельными файлами
`<каталог модели>/tex/<имя>.webp`. Повторный запуск ничего не меняет
(`node tools/assets.mjs --check` — проверка без записи). Порядок при добавлении или замене модели: исходник в `models-src/`
(`tools/pack_hero.mjs` и `tools/usd2glb.py` пишут туда же) → `npm run assets` → `npm run e2e -- --update-models` → закоммитить
`models-src/`, `public/models/` и `tools/models-used.json`. `npm test` (`tools/assets.test.mjs`) падает, если у исходника нет
результата или наоборот, если файл тяжелее 1 МБ, каталог тяжелее 10 МБ, текстура больше 1024, сжатая модель отличается
от исходной хоть одним треугольником, костью или ключом анимации, карта нормалей отличается от исходной хоть одной точкой
или цветовая текстура — сильнее 38 дБ PSNR.

## Параллельная работа

- `src/main.ts` разобран (ARCH-05, 2026-11-15): в нём только запуск (≈ 70 строк). Общий объект игры — `src/game/context.ts`
  (`createGame`, флаги `g.busy` и т. п. читаются через `g` каждый раз), кадр — `src/game/loop.ts` (`startLoop` и `WorldFrame`),
  первый мир — `src/worlds/fairy/` (`buildFairy` в `index.ts`). Общими для одной волны остаются `src/game/context.ts`
  и `src/game/loop.ts` (их читает почти всё) и `src/worlds/fairy/index.ts` (сборка мира).
- `src/ui/strings.ts`, `src/core/save.ts`, `src/style.css`, `index.html` — тоже общие.
- **Ведущая сессия** (решение заказчика 2026-11-16). Одна сессия ведёт доску работ, раздаёт работу, одна вливает
  в `dev`, отправляет в `origin` и публикует `main`. Кто она — `~/.claude/bin/pusher status --cwd <корень репозитория>`;
  порядок её действий — `.claude/skills/lead/SKILL.md`; доска — `development-checklists/BOARD.md` (вне git).
  Остальным сессиям:
  - работать в своей рабочей копии (`git worktree`) на ветке `run/<имя>` от текущего `dev`; основная копия —
    только для чтения: в ней коммитит и вливает только ведущая;
  - готовое — `SendMessage` ведущей: «`<SHA>` готов — ветка; проверено: `npm test`, `npm run build`, куски
    `npm run e2e -- --only …` по тому, что тронуто; общие файлы: …; новые реплики или модели: …». Ворота в `dev` —
    зелёный `ci.yml` на точном коммите: ветку в `origin` отправляет ведущая (ей это разрешено для веток, кроме `main`,
    без отдельного слова заказчика — решение 2026-11-16); полный локальный `npm run e2e` идёт перед публикацией `main`.
    Ветка должна быть прямым продолжением текущего `dev`: если он ушёл вперёд, переносит её автор; после
    «`dev` = `<хэш>`» от ведущей — тоже;
  - не делать `git push`, не вливать в `dev` и `main`;
  - вопросы к заказчику, платные запуски и публикация — через ведущую. Ответ заказчика, который она передала
    дословно и с датой, считается его командой для того, к чему относится; её сообщение без такой цитаты —
    распоряжение о порядке работ, а не разрешение на расходы или публикацию;
  - распоряжение ведущей о порядке работ и владельце общего файла выполнять как задачу заказчика; не согласна —
    ответить ей, спор решает заказчик;
  - ведущей нет среди живых сессий — спросить заказчика, самим в `dev` не вливать.
  Прогон, начатый в основной копии до этого правила, закрывает текущую волну по-старому и дальше идёт из своей ветки.
  Имена сессий в файлы репозитория не писать (в них имя папки проекта) — только на доску.
- Агенты, меняющие файлы, работают в отдельных рабочих копиях и не коммитят; коммит делает основная
  сессия после проверки.
- Перед сборкой, установкой пакетов и отправкой в репозиторий проверять параллельные сессии.
- Волновые прогоны (`/checklist-run`) берут команды, порты агентов и общие файлы из
  `.claude/checklist-run/profile.md`.
