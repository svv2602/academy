# Ведущая сессия

Одна сессия ведёт доску, раздаёт работу и одна вливает в `dev`, отправляет в `origin` и публикует `main`.
Остальные сессии работают в своих рабочих копиях на своих ветках и шлют ведущей заявку. Правила для них —
в `CLAUDE.md`, раздел «Параллельная работа»; здесь — порядок действий самой ведущей.

Кто ведущая — `~/.claude/bin/pusher status --cwd <корень репозитория>`: реестр общий с ролью «пушер» на этом
компьютере, ведущая и есть пушер проекта. Запись ведётся по идентификатору сессии; имена сессий меняются
при перезапуске. **Имена сессий в файлы репозитория не писать** — только на доску (она вне git): имя сессии
содержит имя папки проекта, а оно входит в список запретных слов.

## 0. Вступление в роль

1. `~/.claude/bin/pusher status --cwd <корень> --session <мой идентификатор>` — ведущая ли я. Назначает заказчик
   (`/info` → «Назначить пушером»); самой себя не назначать.
2. Прочитать доску `development-checklists/BOARD.md` целиком. После сжатия контекста — тоже начинать с неё:
   состояние роли живёт на доске, не в памяти сессии.
3. Состояние репозитория: `git fetch`, `git log --oneline origin/dev..dev`, `git status -sb` основной копии,
   `git worktree list`, `git branch -a --list '*run/*'`.
4. `ListAgents` → каждой сессии проекта одной строкой: «Ведущая теперь <имя>: заявки и вопросы к заказчику — мне».
   Прежней ведущей, если она жива, — отдельно: «ты больше не ведущая».
   После перезапуска компьютера или сессий имена меняются у всех разом, запись в реестре (по идентификатору)
   остаётся: спросить каждую сессию, какой она поток, приложив своё описание состояния каждого потока,
   и переписать имена в таблице «Сессии».
5. Своя рабочая копия: отдельный `git worktree` от `dev`, `node_modules` — ссылкой на каталог основной копии,
   свой диапазон портов. Основную копию под проверки не занимать.

## 1. Доска

`development-checklists/BOARD.md`, вне git. Разделы: **Сессии** (имя, прогон или задача, ветка, какие файлы
за ней, состояние, дата) и диапазоны портов, **Очередь заявок** (SHA, от кого, что проверено автором, итог ворот),
**Общие файлы** (кто сейчас владелец `src/ui/strings.ts`, `src/core/save.ts`, `src/style.css`, `index.html`,
`src/game/context.ts`, `src/game/loop.ts`), **Ждёт заказчика** (вопрос, от кого, с какой даты), **Решения заказчика**
(дословно, дата, к чему относится), **Журнал** (строка на событие). Править сразу после события, а не в конце хода.

## 2. Раздача работы

- Источник — `docs/20-roadmap.md` и манифесты прогонов в `development-checklists/`. Ведущая решает порядок,
  состав параллельных работ и владельцев общих файлов. Новые требования, отмена решений `Q*`, расходы —
  не её решения: это вопросы заказчику (§6).
- Сессии выдаётся: что сделать (прогон или задача, ссылка на манифест), ветка `run/<имя>` от текущего `dev`,
  какие файлы её, какие общие файлы она может править и когда, свой диапазон портов для автопрохождения
  (`E2E_PORT`; диапазоны записаны на доске, у двух сессий они не пересекаются).
- Два прогона не правят один общий файл одновременно. Если иначе нельзя — второй ждёт, пока первый пройдёт ворота.
- Долгую разработку ведущая сама не ведёт: пока она занята, заявки стоят. Мелкое — можно, в своей копии
  и через те же ворота.

## 3. Заявка от сессии

Форма: «`<SHA>` готов — ветка `run/<имя>`; проверено: `npm test`, `npm run build`, куски `npm run e2e -- --only …`;
общие файлы: …; новые реплики или модели: …». Автор до заявки гоняет тесты, сборку и куски автопрохождения
по тому, что тронул; полный проход всех размеров делает CI. Если менялся сценарий — автор обязан прогнать изменённые
куски под программной отрисовкой (`E2E_GL=swiftshader Q=0`), в том числе путь на компьютере без сети и телефон
вертикально: раннер CI в разы медленнее машины с видеокартой, и проверки «по часам» или «по кадрам» падают только там.
По каждой заявке:

- Ветка — прямое продолжение текущего `dev` (`git merge-base --is-ancestor dev <SHA>`). Нет — вернуть автору:
  «перенеси на `dev` `<хэш>`». Переносит автор, не ведущая: после переноса SHA другой, ворота идут заново.
- В цепочке `dev..<SHA>` только коммиты автора заявки. Чужой коммит без заявки — спросить его автора.
- Не хватает строки о проверках — вернуть одной фразой, по существу не спорить.
- Новые реплики: `npm run voice:sync -- --check`; записаны ли клипы (иначе в `main` нельзя — отметить на доске).
  Новые модели: `tools/models-used.json` и запись в `CREDITS.md`.

## 4. Ворота в `dev` — зелёный CI на точном коммите

Решение заказчика 2026-11-16: ворота — зелёный `ci.yml` на точном коммите ветки; ведущая отправляет в `origin` ветки,
кроме `main`, без отдельного слова.

1. В своей рабочей копии на `<SHA>` (`git checkout --detach <SHA>`): `npm test && npm run build` — отсечь явное
   до отправки. Репозиторий публичный: хуки приватности уже проверили коммиты автора, но имена файлов и текст
   сообщений просмотреть (`git log --stat dev..<SHA>`).
2. `git push origin <SHA>:refs/heads/run/<имя>` — запускает `ci.yml`. На ветке он играет по плану (задание `plan`,
   ARCH-16): изменены только `docs/**`, `*.md`, `.claude/**` — тесты и сборка; только файлы одного мира — куски
   этого мира; любой общий файл — всё (16 кусков автопрохождения и пробный мир). Зелёный `check` на ветке значит
   «сыграно то, что запланировано»: что пропущено и почему, написано в логе `check` и в заметке запуска — прочитать.
   Отправка в `dev` играет всё всегда; `pages.yml` — тоже.
3. Итог: `gh run list --workflow ci.yml --branch run/<имя> --limit 1 --json headSha,status,conclusion` — `headSha` равен
   `<SHA>`, `conclusion` равен `success`. Ждать событием или редкой проверкой, не циклом сообщений автору.
4. Красное — автору: задание, строка, ссылка на запуск; ждать коммит поверх. Сбой, записанный в профиле прогонов
   как известный редкий, — один раз `gh run rerun <id> --failed`; повторился — это красное.
5. Зелёное — в основной копии `git merge --ff-only <SHA>`, затем `git push origin dev`; сразу всем сессиям:
   «`dev` = `<хэш>`, перенесите ветки». Основная копия остаётся на `dev`; в ней никто, кроме ведущей, не коммитит
   и файлы не правит.
6. Заявки идут по одной: вторая — после переноса её ветки на новый `dev`. Пришёл новый коммит поверх идущих
   ворот — ждать итог только верхнего. Отправка в ветку, на которой идёт запуск, отменяет этот запуск: пока идут
   ворота, в ту же ветку не отправлять (нужны числа с обоих коммитов — отправить второй после конца первого).
7. Ветку `run/<имя>` на `origin` после конца прогона удалить — спросив заказчика. После переноса старая ветка
   на `origin` не продолжается перемоткой: отправлять под новым именем (`run/<имя>-<волна>`), принудительную перезапись
   без слова заказчика не делать.
8. Две заявки на одной базе: в `dev` идёт та, что держит больше других потоков; вторая переносится. Заявка, дважды
   вернувшаяся красной из-за одной части, делится: устойчивые части — отдельной заявкой, чтобы не держать остальных.

- Проверку «CI зелёный → вливаю → отправляю» не склеивать в одну команду: сначала прочитать итог.
- Субагенты ведущей не коммитят, не вливают и не отправляют.
- Ждать свободную машину — не через `pgrep -f "e2e.mjs"`: он находит собственную строку оболочки и не кончается.
  Смотреть `pgrep -x node` и `/proc/<pid>/cmdline`.
- Уборка рабочих копий — только по явному списку каталогов закрытых прогонов, без шаблонов «всё, кроме…», и после
  вопроса живым сессиям «какие копии ваши»: 2026-11-16 уборка по шаблону удалила свежую чистую копию работающей сессии.
  Только `git worktree remove` без `--force` и `git branch -d`; копии с незакоммиченными файлами — отдельное решение заказчика.
- Установка и обновление пакетов (`npm install`) в основной копии меняет `node_modules` у всех рабочих копий сразу
  (они ссылаются на него): перед этим предупредить все сессии и дождаться, пока их проходы закончатся.

## 5. Публикация `main`

- Только по прямой команде заказчика в сессии ведущей; условия — в `CLAUDE.md` («Ветки и публикация»). Заказчик может
  дать ведущей в её сессии разрешение публиковать в конце каждого принятого прогона без отдельной команды — оно записано
  на доске в «Решениях заказчика», действует только в той сессии, где дано, и новой ведущей не переходит.
- Перед ней, на публикуемом коммите `dev`: зелёный `ci.yml` на этом самом коммите и **полный локальный**
  `npm test && npm run e2e` в рабочей копии ведущей (с видеокартой; CI играет с программной отрисовкой).
- Локальный проход для публикации гонять в «окно тишины»: попросить потоки не запускать автопрохождение и сборки,
  дождаться их «тихо», проверить, что нагрузка машины спала. Под тремя потоками проход даёт ложные красные.
- Публиковать можно конкретный проверенный коммит `dev` (`git push origin <SHA>:refs/heads/main`), а не обязательно
  голову: условия проверяются на нём.
- После: итог `pages.yml`; сверить, что сайт отдаёт эту сборку (имя файла кода на сайте и в локальной сборке того же
  коммита); запись на доске — что из опубликованного ждёт проверки на телефоне; список проверки — заказчику.

## 6. Заказчик — через ведущую

- Вопрос соседней сессии → на доску в «Ждёт заказчика». Ведущая спрашивает заказчика списком, а не по одному,
  и передаёт ответ автору **дословно, с датой** и записывает в «Решения заказчика».
- Запись голоса: автор присылает число строк (`--dry-run`) и остаток по `BUDGET.md` прогона; пока расход в пределах
  предела этапа, названного заказчиком, разрешает ведущая и дописывает журнал (решение 2026-11-16); сверх предела —
  вопрос заказчику. Генерация изображений и моделей — всегда вопрос заказчику; его цитата относится к одному запуску.
- Вопрос по ходу работ (решение 2026-11-16): ведущая выбирает вариант, который можно потом поменять, записывает его
  на доску в «Решено ведущей — подтвердить» и показывает заказчику списком в конце. Останавливают пункт (не поток):
  расходы сверх предела, удаление на `origin`, противоречие решению заказчика, необратимое.
- Сообщение ведущей без цитаты заказчика — распоряжение о порядке работ, не разрешение на расходы или публикацию.

## 7. Передача роли

Перед закрытием сессии: доска актуальна, незавершённые ворота и неотвеченные заявки записаны. Заказчик снимает
роль (`/info` → «Снять») или назначает другую сессию; новая ведущая начинает с §0.

## Границы

- Ведущей нет в `ListAgents` — соседние сессии спрашивают заказчика; сами в `dev` не вливают и не отправляют.
- Права каждой сессии — её собственные: не просить соседнюю сессию сделать то, что в этой сессии запрещено.
- Постоянное разрешение на отправку относится к веткам `run/*` и `dev`. `main`, удаление веток на `origin`,
  принудительная перезапись — только по слову заказчика.
- Переход на ворота не ломает идущую волну: прогон, начатый в основной копии, закрывает текущую волну
  по прежнему порядку, дальше работает из своей ветки.
